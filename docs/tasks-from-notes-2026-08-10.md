| | **طلبات الشراء** (تاسك 11) | **أوامر الشراء** (M29) |

## 3️⃣3️⃣ 🐞 بداية اليوم عند ١٢:٠١ ص — سبب مؤكَّد

**المطلوب (صفحة 1):** «يتم الدخول إلى اليوم/التاريخ عند الساعة ١٢:٠١ ص.»

**نتيجة الفحص — سبب مؤكَّد:** التطبيق يعمل بتوقيت **UTC**:

```
config/app.php:68   'timezone' => env('APP_TIMEZONE', 'UTC')
.env:5              APP_TIMEZONE=UTC
```

والسعودية **UTC+3**. النتيجة أن اليوم في النظام يبدأ الساعة **٣:٠٠ صباحاً**
بتوقيت الرياض لا منتصف الليل:

- `ResolveReportScope` يبني المدى من `Carbon::today()` — أي يوم UTC.

**مكان التنفيذ:**
- `.env` و`.env.example` و`config/app.php:68`
- `app/Actions/Report/ResolveReportScope.php`
- كل `DB::raw('DATE(...)')` في `DailyReportController` و`CommissionReportController` و`SalesReportController` و`AnalyticsController`

**البرومبت:**

## 3️⃣7️⃣ ⚠️ السعر المُدخل شامل ضريبة القيمة المضافة — ✅ منفّذ (10/08/2026)

**المطلوب (صفحة 3):** «يكون المبلغ الذي يسجل من قِبل الموظف **شامل ضريبة القيمة المضافة**، أي المبلغ الإجمالي يكون **١٠٠ ريال وليس ١١٥ ريال**.»

**المثال الذي وسمه العميل بنفسه** (خدمة بسعر 100، عمولة صاحب العمولة 10%، خامات 50، عمولة موظف 50%):

| البند | الحالي | المطلوب | وسم العميل |
|---|---|---|---|
| المجموع الفرعي | 100.00 | **86.95** | 🔴 خطأ حالياً |
| الضريبة (15%) | 15.00 | **13.05** | 🔴 خطأ حالياً |
| **الإجمالي** | **115.00** | **100.00** | 🔴 خطأ حالياً |
| عمولات أصحاب العمولة | 8.70 | 8.70 | 🟢 صحيح حالياً |
| تكلفة الخامات | 50.00 | 50.00 | 🟢 صحيح حالياً |
| عمولة الموظف | 18.48 | 18.48 | 🟢 صحيح حالياً |

**قراءة الفحص — لماذا هذا التقسيم منطقي تماماً:** العمولات الثلاث محسوبة **أصلاً**
على القيمة الصافية من الضريبة منذ تاسك 6:

```php
// CalculateServiceInvoiceAction.php:206-215
$taxableBase = round($afterAgent - $pointsDiscount, 2);   // 100.00
$vatAmount   = round($taxableBase * $vatPct / 100, 2);    // 15.00  ← تُضاف فوق المئة
$total       = round($taxableBase + $vatAmount, 2);       // 115.00 ← ما يعترض عليه العميل
$netBeforeVat = round($taxableBase / (1 + $vatPct / 100), 2); // 86.96 ← الأساس الصحيح
```

`8.70 = 10% × 86.96` و`18.48 = 50% × (86.96 − 50)` — أي **`netBeforeVat` هو ما يعتبره العميل
المجموع الفرعي الصحيح**. فالمطلوب حرفياً: نقل `netBeforeVat` من كونه أساس عمولات
**داخلياً** إلى كونه **المجموع الفرعي المعلن** للعميل، وجعل `taxableBase` هو الإجمالي.

**الأثر يمسّ الكود مرتين (خادم + واجهة) وفي مسارين (خدمات ومنتجات):**

| الملف | السطر | الحالي |
|---|---|---|
| `CalculateServiceInvoiceAction.php` | 206-215 | `total = base + vat` |
| `CreateProductInvoiceAction.php` | 150-156 | نفس المعادلة |
| `pos/service/index.tsx` | 265, 285-286 | نفس المعادلة في الواجهة الحيّة |
| `pos/product/index.tsx` | — | نفس الشيء |
| `invoices/print.tsx` | 32-33, 170-171 | `grossVat`/`grossTotal` قبل الخصم |

**مكان التنفيذ:** الملفات أعلاه + كل ما يقرأ `total_amount`: الدفعات (`RecordInvoicePaymentAction`)، الولاء (`FLOOR(total × rate)`)، المرتجعات، حمولة ZATCA QR.

**ما نُفّذ (10/08/2026):**

1. **الخادم — المعادلة انعكست** في `CalculateServiceInvoiceAction` و
   `CreateProductInvoiceAction`، بصيغة واحدة في الاثنين:
   ```php
   $total        = round($afterAgent - $pointsDiscount, 2);   // ما يدفعه العميل
   $netBeforeVat = round($total / (1 + $vatPct / 100), 2);
   $vatAmount    = round($total - $netBeforeVat, 2);          // طرح لا ضرب
   ```
   الضريبة تُحسب بالطرح لا بالضرب في الصافي، فلا يظهر فرق قرش أبداً.
   عمود `subtotal` بقي مجموع الأسطر كما هي (شاملة) بلا تعديل.
2. **العمولات لم تتغيّر بحرف**: `netBeforeVat` هو نفسه رقماً (كان
   `round($taxableBase / (1 + vat/100), 2)` وصار `round($total / …)` و`$total` هو
   `$taxableBase` نفسه). اختبارات العمولة القائمة (43.48 و2.61 و34.79 و33.48) مرّت
   بلا تعديل رقم واحد فيها — وهذا صمّام الأمان للتغيير كله.
3. **الواجهة — اشتقاق واحد**: `invoiceTotals()` في `resources/js/lib/invoice.ts`
   يُخرج المجموع الفرعي والخصومات صافيةً من الضريبة بحيث يجمع العمود بالقرش:
   `المجموع الفرعي − الخصومات + الضريبة = الإجمالي`. يستعمله:
   `invoices/show.tsx`، و`components/invoices/print-totals.tsx` (الحراري)،
   و`invoices/print.tsx` (A4)، وشاشتا نقطة البيع.
   وأُضيف تحت ترويسة عمود السعر في `components/pos/cart-table.tsx` تنويه
   «شامل الضريبة»، وصار عنوان السطر الأخير «الإجمالي (شامل الضريبة)».
4. **الطباعة**: حُذف `grossVat`/`grossTotal` — كانا يعيدان الاحتساب من `subtotal`
   ويتجاهلان الخصومات تماماً. المطبوع الآن يقرأ `vat_amount` و`total_amount`
   المخزّنين، فيوافق شاشة العرض ورمز ZATCA (الذي يقرأ العمودين نفسيهما، فلم يحتج
   أي تعديل).
5. **التقرير اليومي**: `invoiceDaily` كان يحسب الصافي بـ `subtotal − الخصومات`،
   وهي تساوي الإجمالي شامل الضريبة بعد التغيير. صار `total_amount − vat_amount` —
   صيغة صحيحة للفواتير القديمة والجديدة معاً، فلا تحتاج البيانات التاريخية أي معالجة.
   (تقرير المبيعات يعرض «قبل الخصم» و«الخصومات» و«الضريبة» أعمدةً مستقلة ولا يشتقّ
   منها صافياً، فلم يتأثر.)
6. **لا migration بيانات**: الفواتير المحفوظة لم تُمسّ ولم يُعد احتسابها.
7. **الاختبارات**: ملف جديد `tests/Feature/Pos/VatInclusivePricingTest.php` —
   مثال العميل (100 ← إجمالي 100، ضريبة 13.04، صافي 86.96)، وثبات
   `net + vat = total` عبر 20 سعراً حرجاً، والإجمالي بعد الخصم شامل الضريبة،
   وفرع بضريبة صفر. وحُدّثت توقّعات 8 ملفات اختبار قائمة (نقطة البيع والولاء
   والتقرير اليومي) — كلها أرقام عرض، ولا واحدة منها رقم عمولة.

> **فرق القرش عن ورقة العميل:** ورقته تكتب 86.95 والحساب الدقيق 86.9565. المعتمد
> هو التقريب لأقرب قرش (86.96) وطرح الضريبة منه (13.04) حتى يبقى المجموع 100.00
> بالضبط — النظام يعرض 86.96 لا 86.95.

## 3️⃣8️⃣ طريقة الدفع إلزامية وإرفاق الإيصال في مودال الدفعة — 🐞 سبب مؤكَّد

**المطلوب (صفحة 4):**

**نتيجة الفحص — عطلان مؤكَّدان:**

1. **الإيصال:** الميزة موجودة على **الفاتورة** لا على **الدفعة**. نقطة البيع تقرأ

   ```php
   // StoreInvoicePaymentRequest.php:28
   'payment_method_id' => ['nullable', 'integer', Rule::in(...)],
   ```

- نمط المرفق الجاهز: `app/Http/Controllers/InvoiceReceiptController.php` + Media Library

**البرومبت:**
```

2) إن كان الفرع بلا طرق دفع مفعّلة، اعرض في المودال تنبيهاً «لا توجد طرق دفع
   مفعّلة لهذا الفرع» وعطّل زر الحفظ بدل إخفاء المنتقي.
3) الإيصال: كرّر نمط الفاتورة على الدفعة. مرّر requiresAttachment ضمن
```
